# Migration: 0.4 → 0.5 (Botan 3 + subcommand CLI + capability policy)

The 0.5 series is a major rewrite. The most user-visible changes:

1. **Botan 2 → Botan 3** — adds SHA-3, AES-GCM-SIV, Argon2id.
2. **clap 2 → clap 4** — flat CLI → subcommand-style (`enprot encrypt`, etc.).
3. **Capability policy** — new `--policy-file` for restricting algorithms.

## What changed

### CLI shape

Before (0.4.x):

```
enprot -e -w WORD -k PASSWORD input.ept
```

After (0.5.x+):

```
enprot encrypt -w WORD -k WORD=PASSWORD input.ept
```

Common args (`-v`, `-k`, `-c`, `--policy`) moved to `global = true`
so they work before or after the subcommand name. Encrypt-specific
options (`--pbkdf`, `--cipher`) live under the `encrypt` subcommand.

### Cipher naming

Before: cipher names were case-insensitive (`AES-256-SIV`).
After: cipher names are lowercase, hyphen-separated (`aes-256-siv`).

### PBKDF extfield format

Before: `pbkdf=pbkdf2-sha256(1000)` — ad-hoc parens syntax.
After: `pbkdf=$pbkdf2-sha256$i=1000$<salt-b64>` — PHC string format.

The decrypt path auto-detects both formats; old blobs still decrypt.
The encrypt path always emits the new format.

### Config file

Before: `~/.enprotrc` (INI-like).
After: `.enprot.toml` (TOML). Generated by `enprot init`.

## Why

- **Botan 3** unlocks modern primitives (SHA-3 content addressing,
  AES-GCM-SIV for misuse-resistant AEAD, Argon2id for memory-hard
  PBKDF). Botan 2 is end-of-life.
- **Subcommand CLI** scales to the new feature set (manifest, attest,
  audit-log, snapshot, pin, etc.). The flat CLI was at capacity.
- **PHC string format** is a widely-adopted standard that encodes the
  salt and parameters in a self-describing string. Easier to
  parse, validate, and document.
- **Capability policy** lets enterprise users restrict algorithms to
  a vetted set (e.g., FIPS-approved only). Required for compliance
  use cases.

## Before / after

### CLI invocation

```sh
# Before
enprot -e -w WORD -k hunter2 -c aes-256-gcm-siv input.ept > out.ept
enprot -d -w WORD -k hunter2 out.ept > restored.ept

# After
enprot encrypt -w WORD -k WORD=hunter2 --cipher aes-256-gcm-siv input.ept > out.ept
enprot decrypt -w WORD -k WORD=hunter2 out.ept > restored.ept
```

### Encrypted block

```ept
// Before (0.4.x)
// <( ENCRYPTED WORD pbkdf=pbkdf2-sha256(1000) cipher=AES-256-SIV )>
// <( DATA <base64> )>
// <( END WORD )>

// After (0.5.x+)
// <( ENCRYPTED WORD pbkdf:$pbkdf2-sha256$i=1000$MDEyMzQ1Njc4OWFiY2RlZg cipher:aes-256-siv )>
// <( DATA <base64> )>
// <( END WORD )>
```

## Detection

The `enprot doctor` command (TODO #42, future) will scan and report:

    $ enprot doctor path/to/files.ept
    WARN  path/to/files.ept:14  pbkdf extfield uses legacy format
    HINT  re-encrypt with `enprot encrypt -w WORD path/to/files.ept`

For now, manual inspection:

```sh
grep -l 'pbkdf=pbkdf2' path/to/files/*.ept
grep -l 'cipher=AES' path/to/files/*.ept
```

## Migration steps

### For CLI users

1. Update scripts that invoke `enprot -e` / `enprot -d` to the new
   subcommand form.

   ```sh
   # Old
   enprot -e -w WORD -k PASS file
   # New
   enprot encrypt -w WORD -k WORD=PASS file
   ```

2. Lowercase cipher names: `AES-256-SIV` → `aes-256-siv`.

3. Update any wrapper scripts that parse enprot's stdout (the
   subcommand restructure changes stderr log lines).

### For file users

1. **Files encrypted by 0.4.x still decrypt in 0.5.x.** The decrypt
   path auto-detects the legacy PHC format.
2. To upgrade to the new format, re-encrypt:

   ```sh
   enprot decrypt -w WORD -k WORD=PASS old.ept > plaintext
   enprot encrypt -w WORD -k WORD=PASS plaintext > new.ept
   rm plaintext
   ```

3. The re-encryption produces the new PHC format and lowercased
   cipher name.

### For FFI users

1. The FFI API `enprot_process(config_json)` is unchanged in shape.
2. The `config_json` schema accepts both old and new field names
   during a transition window; the old names will be removed in 0.6.
3. Migrate to the new field names now:

   ```diff
   {
   -  "encrypt": true,
   +  "operation": "encrypt",
      "word": "WORD",
      ...
   }
   ```

## Compatibility

- **Decrypting old files**: 0.5.x fully supports decrypting files
  encrypted by 0.4.x (the parser auto-detects the pbkdf format).
- **Encrypting in old format**: not supported. 0.5.x always emits
  the new format.
- **Reverse**: 0.4.x cannot decrypt files encrypted by 0.5.x (the
  new PHC format isn't recognized). If you need cross-version
  compatibility, stay on 0.4.x for both sides.
